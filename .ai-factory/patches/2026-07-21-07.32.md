# Slowed down mobile menu opening animation

**Date:** 2026-07-21 07:32
**Files:** theme/vite-wordpress-starter-theme/assets/src/scss/layout/_header.scss, theme/vite-wordpress-starter-theme/assets/src/js/components/mobileNav.js
**Severity:** low

## Problem

Mobile nav panel opened too fast (0.45s), user wanted a slower, more deliberate open while keeping the close speed snappy.

## Root Cause

Not a bug — a UX timing preference. Worth recording because the opening transition duration is coupled to a second, independent system: the GSAP scan-line effect (`playScanEffect` in mobileNav.js) starts via `gsap.timeline({ delay })`, and that delay is a hardcoded literal that must equal the CSS transition duration for the panel. The two live in different files/languages (SCSS vs JS) with no shared source of truth, so changing one without the other desyncs the scan-line start from the panel's actual slide-in completion.

## Solution

- `_header.scss` `.nav--mobile-overlay`: both the base (closed) rule and `.is-open` transition duration changed 0.45s → 1.2s. Initially applied asymmetrically (open only) per an earlier request, then symmetrized to also slow the close.
- `mobileNav.js` `playScanEffect()`: `gsap.timeline({ delay: 0.45 })` → `{ delay: 1.2 }` to match the new opening duration.
- Added comments at both sites cross-referencing each other, since this coupling isn't visible from either file alone.

## Prevention

- When touching `.nav--mobile-overlay` transition durations in `_header.scss`, always check `mobileNav.js` `playScanEffect()`'s `gsap.timeline({ delay })` and vice versa — they must stay equal.
- Consider extracting the duration into a single shared constant (e.g. a CSS custom property read via `getComputedStyle` in JS) if this pair changes again.
