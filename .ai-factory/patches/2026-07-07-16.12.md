# AOS fade-in on .s-process--top .section-title triggers far too late on mobile

**Date:** 2026-07-07 16:12
**Files:** theme/vite-wordpress-starter-theme/assets/src/js/components/servicesAccordion.js
**Severity:** medium

## Problem

On mobile, the `data-aos="fade-in"` animation on `.section-title` inside
`.s-process.s-process--top` only fired once the element had scrolled almost
all the way to the top of the viewport, instead of fading in as it entered
the screen from the bottom (the expected AOS `top-bottom` behavior).

Confirmed via live scroll instrumentation in Chrome DevTools (375x812
mobile viewport): the `.aos-animate` class was only added when the
element's `getBoundingClientRect().top` reached ~193px (near the top of
an 812px-tall viewport), instead of the expected ~692px
(`windowHeight - AOS default offset(120)`).

## Root Cause

`initServicesAccordion()` (`main.js`, called synchronously on
`DOMContentLoaded`, right after `initHeroAnimations()` which calls
`AOS.init()`) sets up the initial "one item expanded, rest collapsed"
accordion state via jQuery. `setActiveItem($item, animate)` was called
with `animate = false` for this initial call, but the code still invoked
`$desc[isActive ? 'show' : 'hide'](250)` — passing a duration to
`.show()`/`.hide()` makes jQuery animate them regardless of the
`animate` flag's intent.

This meant 4 of 5 `.services-list__desc` panels (each ~100-124px tall)
collapsed via an animated 250ms slide *after* `DOMContentLoaded`,
shrinking total document height by ~488px shortly after page load —
confirmed by probing `document.documentElement.scrollHeight` over time
(9459px at `DOMContentLoaded` → 9009px ~1.5s later).

AOS caches each element's scroll-trigger offset once, at `DOMContentLoaded`
(`startEvent: 'DOMContentLoaded'` in `AOS.init()`), and never refreshes
automatically for layout shifts caused by scripts (only for DOM
mutations via its internal MutationObserver, which don't cover
`display: none` height changes from jQuery `.hide()`). So every element
below the services section — including `.s-process--top .section-title`
— kept a stale trigger point computed against the taller, pre-collapse
layout. On mobile's short viewport, needing ~488px of "extra" scroll to
satisfy a stale trigger is a large fraction of the total scroll distance,
so the fade-in visibly fires far too late.

## Solution

Fixed `setActiveItem()` in `servicesAccordion.js` so the non-animated
(`animate = false`) branch truly applies the initial expand/collapse
state instantly (`.show()` / `.hide()` with no duration) instead of
silently animating over 250ms. This keeps the DOM height stable by the
time `AOS.init()`'s cached offsets matter, removing the ~488px stale
delta entirely.

Verified via Chrome DevTools scroll instrumentation: the trigger point
for `.s-process--top .section-title` moved from `top ≈ 193px` to
`top ≈ 683-693px`, matching AOS's expected default `windowHeight(812) -
offset(120) = 692px`.

## Prevention

- When passing a jQuery animate/instant flag into `.show()`/`.hide()`,
  never pass a duration argument on the "instant" branch — `.show(250)`
  and `.hide(250)` are always animated regardless of any wrapping
  conditional.
- Any DOMContentLoaded-time script that changes document height
  (accordions, sliders, lazy content) should either apply its initial
  state synchronously/instantly, or call `AOS.refresh()` (already used
  in `heroAnimations.js` via `AOS.refreshHard()` for the footer form)
  after the layout settles — otherwise `data-aos` elements further down
  the page will get stale trigger offsets.
- When debugging "AOS animation triggers at the wrong scroll position,"
  instrument `document.documentElement.scrollHeight` over time after
  load rather than guessing — a shrinking/growing page height after
  `DOMContentLoaded` is the classic cause.
